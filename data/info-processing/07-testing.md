# 애플리케이션 테스트 관리

## 테스트 원리 (7원칙)

- **결함 존재 증명** — 테스트로 오류가 숨어 있다는 사실은 보일 수 있지만, 오류가 하나도 없다는 것은 보일 수 없다는 원리.
- **완벽한 테스트 불가능 (Exhaustive Testing is Impossible)** — 입력·경로 조합이 너무 많아 모든 경우를 다 시험할 수 없으므로, 위험도와 우선순위로 범위를 정해야 한다는 원리.
- **초기 집중 (Early Testing)** — 결함은 늦게 발견할수록 고치는 비용이 커지므로, 요구·설계 단계부터 시험 활동을 시작해야 한다는 원리.
- **결함 집중 (Defect Clustering)** — 발견되는 오류의 대부분이 전체 중 소수의 특정 모듈에 몰려 나타난다는 원리.
  - 파레토 법칙(80:20)과 연결된다
- **살충제 패러독스 (Pesticide Paradox)** — 같은 테스트 케이스를 계속 반복하면 더는 새 결함을 찾지 못하므로, 케이스를 주기적으로 검토·보강해야 한다는 원리.
- **정황 의존성 (Testing is Context Dependent)** — 소프트웨어의 성격과 사용 환경에 따라 시험 방법과 강도를 달리해야 한다는 원리.
- **오류-부재의 궤변 (Absence-of-Errors Fallacy)** — 결함을 다 고쳤더라도 사용자 요구를 만족하지 못하면 품질이 높다고 할 수 없다는 원리.

## 테스트 레벨 (단통시인)

- **단위 테스트 (Unit Test)** — 구현된 개별 모듈·함수·클래스를 따로 떼어 제대로 동작하는지 검증하는 가장 낮은 수준의 시험.
  - 주로 화이트박스, 드라이버·스텁 사용
- **통합 테스트 (Integration Test)** — 검증된 모듈들을 결합해 가며 모듈 사이의 인터페이스와 상호작용에 결함이 없는지 확인하는 시험.
  - 하향식(스텁)·상향식(드라이버)·빅뱅·샌드위치
- **시스템 테스트 (System Test)** — 완성된 전체 제품이 기능·비기능 요구사항을 실제 운영과 비슷한 환경에서 만족하는지 확인하는 시험.
- **인수 테스트 (Acceptance Test)** — 고객이나 최종 사용자가 요구한 대로 만들어졌는지 직접 확인해 납품을 받아들일지 결정하는 시험.

## 인수 테스트 세부

- **알파 테스트 (Alpha Test)** — 개발자의 장소에서 사용자가 시험하고, 개발자가 옆에서 지켜보며 문제를 기록하는 통제된 환경의 시험.
- **베타 테스트 (Beta Test)** — 실제 사용 환경에서 개발자 없이 사용자가 직접 써 보고, 발견한 문제를 개발자에게 알려 주는 시험.

## V 모델

- **V 모델 (V-Model)** — 폭포수 모형을 확장해 각 개발 단계마다 짝이 되는 테스트 단계를 대응시키고, 검증과 확인을 강조한 모형.
- Q: V 모델에서 요구사항 분석에 대응하는 테스트 — 인수 테스트
- Q: V 모델에서 분석·설계(시스템 설계)에 대응하는 테스트 — 시스템 테스트
- Q: V 모델에서 아키텍처·상세 설계에 대응하는 테스트 — 통합 테스트
- Q: V 모델에서 구현(코딩)에 대응하는 테스트 — 단위 테스트

## 테스트 오라클

- **테스트 오라클 (Test Oracle)** — 시험 결과가 맞는지 틀린지 판정하기 위해 기대 결과를 계산하거나 참조하는 기준이나 장치.
- **참 오라클 (True Oracle)** — 모든 입력값에 대해 기대 결과를 제공해, 발생한 모든 오류를 찾아낼 수 있는 판정 기준.
- **샘플링 오라클 (Sampling Oracle)** — 미리 골라 둔 몇몇 입력값에 대해서만 기대 결과를 제공하는 판정 기준.
- **휴리스틱(추정) 오라클 (Heuristic Oracle)** — 일부 입력값에는 정확한 기대 결과를 주고, 나머지 입력값은 경험에 따른 짐작으로 판단하는 판정 기준.
- **일관성 검사 오라클 (Consistent Oracle)** — 프로그램을 고치기 전과 후의 실행 결과가 같은지 비교해 판단하는 판정 기준.
  - 회귀 테스트에 주로 쓴다

## 화이트박스 테스트

- **화이트박스 테스트 (White-box Test)** — 모듈의 내부 소스 코드와 논리 구조를 들여다보며 경로·조건이 제대로 동작하는지 확인하는 기법.
  - 구조 기반 테스트
- **기초 경로 검사 (Basis Path Testing)** — 맥케이브(McCabe)의 순환 복잡도로 독립 경로 수를 구하고, 그 경로를 모두 한 번 이상 실행해 보는 기법.
  - V(G) = E − N + 2 (E: 간선 수, N: 노드 수)
- Q: 순환 복잡도 V(G)를 구하는 다른 두 방법 — 닫힌 영역 수 + 1, 또는 조건 분기 수 + 1
- **제어 구조 검사 (Control Structure Testing)** — 프로그램의 조건문·반복문·변수 사용 흐름을 중심으로 결함을 찾는 기법들의 묶음.
  - 조건·루프·데이터 흐름 검사
- **조건 검사 (Condition Testing)** — 프로그램 안의 논리식들이 참과 거짓을 모두 갖도록 케이스를 만들어 논리식의 결함을 찾는 기법.
- **루프 검사 (Loop Testing)** — 반복문을 0회·1회·여러 번 등으로 다양하게 돌려 반복 구조의 결함을 찾는 기법.
- **데이터 흐름 검사 (Data Flow Testing)** — 변수가 정의되고 사용되는 위치를 따라가며 경로를 골라 시험하는 기법.

## 블랙박스 테스트

- **블랙박스 테스트 (Black-box Test)** — 내부 코드는 보지 않고 요구사항 명세를 기준으로 입력과 출력만 보며 기능을 확인하는 기법.
  - 명세 기반 테스트
- **동등(동치) 분할 (Equivalence Partitioning)** — 입력 영역을 같은 결과가 나올 것으로 보는 유효·무효 그룹으로 나누고, 그룹마다 대표값으로 시험하는 기법.
- **경계값 분석 (Boundary Value Analysis)** — 오류가 입력 범위의 끝에서 자주 생긴다는 점을 노려 범위의 끝값과 그 바로 안팎의 값을 시험하는 기법.
- **원인-효과 그래프 (Cause-Effect Graph)** — 입력 조건과 출력 결과의 논리 관계를 그래프로 그린 뒤 결정 테이블로 바꿔 효용 높은 케이스를 고르는 기법.
- **오류 예측 (Error Guessing)** — 과거 경험과 감각으로 결함이 숨어 있을 법한 곳을 짐작해 시험하는 기법.
  - 다른 기법이 놓친 부분을 보완한다
- **비교 검사 (Comparison Testing)** — 같은 명세로 만든 여러 버전의 프로그램에 같은 입력을 넣고 결과를 견주어 보는 기법.
- **결정 테이블 테스트 (Decision Table Testing)** — 입력 조건의 조합과 그에 따른 동작을 표로 정리하고, 각 조합을 케이스로 삼는 기법.
- **상태 전이 테스트 (State Transition Testing)** — 이벤트에 따라 시스템이 어떤 모드에서 어떤 모드로 바뀌는지 모델링하고, 그 전환 경로를 시험하는 기법.
- **페어와이즈 테스트 (Pairwise Testing)** — 모든 조합 대신, 어떤 두 변수를 골라도 그 값의 짝이 최소 한 번은 나오도록 케이스를 짜서 수를 줄이는 기법.

## 테스트 기반 분류

- **명세 기반 테스트 (Specification-based Test)** — 요구사항 문서에 적힌 기능을 빠짐없이 케이스로 옮겨 구현을 확인하는 시험.
  - 블랙박스 계열: 동등 분할, 경계값 분석 등
- **구조 기반 테스트 (Structure-based Test)** — 소프트웨어 내부의 논리 흐름을 따라 케이스를 만들어 확인하는 시험.
  - 화이트박스 계열: 구문·결정·조건 커버리지 등
- **경험 기반 테스트 (Experience-based Test)** — 테스터의 직관·지식·과거 이력에 기대어 케이스를 만드는 시험.
  - 예: 오류 예측, 탐색적 테스트, 체크리스트

## 테스트 목적별 분류

- **회복 테스트 (Recovery Test)** — 시스템에 일부러 장애를 일으킨 뒤 정상 상태로 제대로 돌아오는지 확인하는 시험.
- **안전 테스트 (Security Test)** — 외부의 불법 침입으로부터 시스템을 지키는 보안 장치가 제대로 동작하는지 확인하는 시험.
- **강도 테스트 (Stress Test)** — 과도한 요청량이나 자원 요구를 가해, 한계를 넘는 비정상 조건에서 시스템이 어떻게 버티고 무너지는지 확인하는 시험.
- **성능 테스트 (Performance Test)** — 응답 시간·처리량·자원 사용률처럼 시스템이 얼마나 빠르고 효율적으로 일하는지를 측정하는 시험.
- **구조 테스트 (Structure Test)** — 시스템 내부의 논리적 경로와 소스 코드의 복잡도를 평가하는 시험.
- **회귀 테스트 (Regression Test)** — 변경이나 결함 수정 뒤, 그 변경이 기존 기능에 새 결함을 일으키지 않았는지 다시 확인하는 시험.
- **병행 테스트 (Parallel Test)** — 변경된 시스템과 기존 시스템에 같은 데이터를 넣고 두 결과를 비교하는 시험.
- **부하 테스트 (Load Test)** — 사용자 수나 요청량을 단계적으로 늘려 가며 시스템이 견딜 수 있는 최대 처리 한계를 찾는 시험.
- **내구성 테스트 (Endurance Test)** — 오랜 시간 일정한 부하를 계속 걸어 메모리 누수처럼 장시간 운영에서만 드러나는 문제를 찾는 시험.
  - Soak Test라고도 한다
- **스파이크 테스트 (Spike Test)** — 아주 짧은 순간에 사용자를 급격히 늘렸을 때 시스템이 정상 동작하고 다시 회복하는지 확인하는 시험.

## 테스트 커버리지

- **테스트 커버리지 (Test Coverage)** — 시험이 대상의 얼마만큼을 실행하고 검증했는지를 나타내는 비율 지표.
- **기능 기반 커버리지 (Function Coverage)** — 시스템의 전체 기능 가운데 시험으로 실제 확인한 기능이 차지하는 비율.
  - 화면 수 등을 모수로 쓰기도 한다
- **라인 커버리지 (Line Coverage)** — 전체 소스 코드 줄 수 가운데 시험 중에 한 번이라도 실행된 줄 수의 비율.
- **코드 커버리지 (Code Coverage)** — 소스 코드의 구문·분기·조건 등이 시험으로 얼마나 실행되었는지를 측정하는 지표.

## 코드 커버리지 종류

- **구문 커버리지 (Statement Coverage)** — 프로그램의 모든 명령문을 적어도 한 번씩 실행했는지를 따지는 기준.
- **결정(분기) 커버리지 (Decision Coverage)** — 모든 판단문(if·while 등)의 전체 결과가 참과 거짓을 각각 한 번 이상 갖도록 하는 기준.
- **조건 커버리지 (Condition Coverage)** — 전체 결과와 상관없이, 판단문 안의 개별 비교식 하나하나가 참과 거짓을 한 번 이상 갖도록 하는 기준.
- **조건/결정 커버리지 (Condition/Decision Coverage)** — 판단문의 전체 결과와 개별 비교식의 결과가 모두 참·거짓을 한 번 이상 갖도록 하는 기준.
  - 앞의 두 기준을 동시에 만족
- **변경 조건/결정 커버리지 (MC/DC, Modified Condition/Decision Coverage)** — 각 개별 비교식이 다른 비교식과 상관없이 전체 판단 결과를 독립적으로 바꿀 수 있음을 보이도록 케이스를 짜는 기준.
  - 항공 등 안전 필수 소프트웨어에서 요구
- **다중 조건 커버리지 (Multiple Condition Coverage)** — 판단문 안 개별 비교식들의 참·거짓 가능한 모든 조합을 다 시험하는 기준.
  - 비교식이 n개면 2ⁿ개 케이스
- **경로 커버리지 (Path Coverage)** — 프로그램의 시작부터 끝까지 가능한 모든 실행 흐름을 한 번씩 지나도록 하는 기준.

## 테스트 하네스

- **테스트 하네스 (Test Harness)** — 시험을 실행하고 결과를 확인하는 데 필요한 코드·데이터·도구를 모아 둔 환경.
- **테스트 드라이버 (Test Driver)** — 아직 없는 상위 모듈 역할을 대신해 하위 모듈을 호출하고 결과를 받아 오는 임시 프로그램.
  - 상향식 통합 테스트에 사용
- **테스트 스텁 (Test Stub)** — 아직 없는 하위 모듈 자리를 대신해 호출을 받고 미리 정한 값을 돌려주는 임시 모듈.
  - 하향식 통합 테스트에 사용
- **테스트 케이스 (Test Case)** — 특정 요구사항을 확인하려고 설계한 입력값·실행 조건·기대 결과의 묶음.
  - 3요소: 입력값, 실행 조건, 기대 결과
- **테스트 시나리오 (Test Scenario)** — 여러 케이스를 실제 사용 흐름에 맞춰 순서대로 엮어 놓은 동작 절차.
- **테스트 슈트 (Test Suite)** — 같은 대상이나 목적을 위해 실행할 여러 케이스를 한데 모은 집합.
- **테스트 스크립트 (Test Script)** — 케이스의 실행 순서와 절차를 자동으로 돌릴 수 있게 적어 둔 명세나 코드.
- **목 오브젝트 (Mock Object)** — 실제 협력 객체 대신 넣는 가짜 객체로, 미리 정해 둔 조건이 오면 예정된 응답과 행동을 하도록 꾸민 것.

## 분석 도구

- **정적 분석 도구 (Static Analysis Tool)** — 프로그램을 실행하지 않고 소스 코드만 살펴 코딩 규칙 위반·잠재 결함·복잡도를 찾아내는 도구.
  - 예: PMD, SonarQube, Cppcheck, Checkstyle
- **동적 분석 도구 (Dynamic Analysis Tool)** — 프로그램을 실제로 실행하면서 메모리 누수·스레드 결함·성능 문제를 찾아내는 도구.
  - 예: Valgrind, Avalanche
- **테스트 자동화 도구 (Test Automation Tool)** — 케이스 실행·결과 비교·보고처럼 반복되는 시험 작업을 자동으로 처리해 주는 도구.
  - 유형: 정적 분석, 테스트 실행, 성능 테스트, 테스트 통제 도구

> PMD·SonarQube·Cppcheck·Checkstyle은 실행 없이 코드만 검사하므로 모두 정적 분석 도구다.

## 애플리케이션 성능 지표 (처응경자)

- **처리량 (Throughput)** — 일정 시간 동안 애플리케이션이 처리해 낸 트랜잭션(요청)의 수로, 단위 시간당 작업량.
- **응답 시간 (Response Time)** — 사용자가 요청을 보낸 순간부터 첫 응답이 돌아오기까지 걸린 시간.
- **경과 시간 (Turnaround Time)** — 요청을 보낸 순간부터 애플리케이션이 처리를 다 끝내고 결과를 모두 돌려줄 때까지 걸린 시간.
- **자원 사용률 (Resource Usage)** — 요청을 처리하는 동안 CPU·메모리·네트워크 같은 자원을 얼마나 쓰는지 나타내는 비율.

## 소프트웨어 품질 특성 (ISO/IEC 9126) (기신사효유이)

- **기능성 (Functionality)** — 소프트웨어가 명시된 요구와 암묵적 요구를 만족하는 기능을 제공하는 정도.
  - 부특성: 적합성·정확성·상호운용성·보안성·준수성
- **신뢰성 (Reliability)** — 정해진 조건에서 일정 기간 동안 고장 없이 요구된 수준의 성능을 유지하는 정도.
  - 부특성: 성숙성·결함 허용성·회복성
- **사용성 (Usability)** — 사용자가 소프트웨어를 쉽게 이해하고 배우고 조작할 수 있으며 매력을 느끼는 정도.
  - 부특성: 이해성·학습성·운용성·친밀성
- **효율성 (Efficiency)** — 주어진 조건에서 투입한 시간·메모리 같은 자원에 비해 적절한 성능을 내는 정도.
  - 부특성: 시간 반응·자원 활용
- **유지보수성 (Maintainability)** — 요구가 바뀌거나 결함이 생겼을 때 소프트웨어를 분석·수정·검증하기 쉬운 정도.
  - 부특성: 분석성·변경성·안정성·시험성
- **이식성 (Portability)** — 소프트웨어를 다른 하드웨어나 운영체제로 옮겨도 큰 수정 없이 동작할 수 있는 정도.
  - 부특성: 적응성·설치성·공존성·대체성

> 후속 표준 ISO/IEC 25010은 호환성·보안성을 더해 8개 특성으로 늘렸다.
