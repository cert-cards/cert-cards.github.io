# 데이터베이스

## 데이터베이스와 관리 주체

- **데이터베이스 (Database)** — 한 조직의 여러 업무에 필요한 데이터를 중복을 줄여 한곳에 모아 두고, 여러 사용자와 응용 프로그램이 함께 쓰도록 관리하는 데이터의 집합
- **DBMS (Database Management System)** — 사용자와 데이터 사이에서 데이터의 정의·조작·제어 기능을 제공해 종속성과 중복성 문제를 해결하는 관리 소프트웨어
  - 필수 기능 3가지: 정의·조작·제어
- **DBA (Database Administrator)** — 시스템 전체에 책임을 지고 스키마 정의, 접근 권한 부여, 백업·회복, 성능 감시 등을 맡는 사람 또는 조직
- **시스템 카탈로그 (System Catalog)** — 테이블·뷰·인덱스·사용자·권한 등 시스템 안의 모든 객체 정보를 시스템이 스스로 만들고 유지하는 테이블 모음. 사용자는 조회만 할 수 있다
  - 데이터 사전(Data Dictionary)이라고도 한다
- **메타 데이터 (Metadata)** — 데이터의 구조·형식·의미·제약처럼 데이터 자체를 설명해 주는 데이터. 카탈로그에 저장된다

## 데이터베이스의 정의 4요소 (공저통운)

- **공유 데이터 (Shared Data)** — 여러 응용 프로그램과 사용자가 동시에 함께 꺼내 쓸 수 있도록 제공되는 데이터
- **저장 데이터 (Stored Data)** — 디스크처럼 컴퓨터가 직접 접근할 수 있는 저장 매체에 기록되어 있어 필요할 때 읽고 쓸 수 있는 데이터
- **통합 데이터 (Integrated Data)** — 흩어진 데이터를 하나로 모으고 중복을 최소화해 관리하는 데이터. 꼭 필요한 통제된 중복만 허용한다
- **운영 데이터 (Operational Data)** — 조직이 고유한 업무를 수행하는 데 반드시 필요해서 존재 가치가 분명한 데이터

## 스키마

- **스키마 (Schema)** — 데이터의 구조, 데이터 간 관계, 제약 조건을 기술한 명세. 데이터 사전에 저장되며 시간에 따라 잘 바뀌지 않는다
  - 특정 시점의 실제 값 모음은 인스턴스

## 3계층 스키마 (외개내)

- **외부 스키마 (External Schema)** — 개별 사용자나 응용 프로그램이 바라보는 데이터의 일부 논리 구조. 여러 개 존재할 수 있으며 서브 스키마·사용자 뷰라고도 한다
- **개념 스키마 (Conceptual Schema)** — 조직 전체 관점에서 모든 데이터와 관계, 제약 조건, 접근 권한, 보안 정책을 정의한 논리 구조. 하나만 존재한다
- **내부 스키마 (Internal Schema)** — 저장 장치 관점에서 레코드 형식, 필드 크기, 인덱스, 저장 순서 등 데이터가 실제로 저장되는 방식을 정의한 구조

## 데이터베이스 설계

- Q: 데이터베이스 설계 순서 — 요구 조건 분석 → 개념적 설계 → 논리적 설계 → 물리적 설계 → 구현
- **개념적 설계 (Conceptual Design)** — 현실 세계의 정보를 추상화해 특정 DBMS와 무관한 모델로 표현하는 단계. E-R 다이어그램 작성과 트랜잭션 모델링을 한다
- **논리적 설계 (Logical Design)** — 앞 단계의 모델을 목표 DBMS가 지원하는 구조(예: 관계형 테이블)로 변환하는 단계. 정규화와 스키마 평가·정제, 트랜잭션 인터페이스 설계를 한다
- **물리적 설계 (Physical Design)** — 테이블을 실제 저장 장치에 어떻게 둘지 정하는 단계. 레코드 형식, 인덱스 같은 접근 경로, 저장 공간 배치를 결정하고 반정규화를 검토한다

## 데이터 모델

- **데이터 모델 (Data Model)** — 현실 세계의 정보를 컴퓨터가 다룰 수 있도록 단순화·추상화해 개념적으로 표현한 도구
- Q: 데이터 모델의 구성 요소 3가지 — 구조(Structure), 연산(Operation), 제약 조건(Constraint)
  - 구조=정적 성질, 연산=실제 값을 처리하는 동적 성질, 제약 조건=저장 가능한 값에 대한 논리적 제한
- Q: 데이터 모델에 표시해야 할 3요소 — 개체, 속성, 관계
- **개체 (Entity)** — 현실 세계에서 독립적으로 존재하며 다른 것과 구별되는, 저장할 가치가 있는 대상. 하나 이상의 속성으로 이루어진다
- **E-R 모델 (Entity-Relationship Model)** — 1976년 피터 첸(P. Chen)이 제안한 개념적 모델로, 현실 세계를 사물과 그들 사이의 연관으로 나타내고 다이어그램으로 시각화하는 방식
- Q: E-R 다이어그램에서 사각형 — 개체 타입
- Q: E-R 다이어그램에서 타원 — 속성
- Q: E-R 다이어그램에서 마름모 — 관계 타입
- Q: E-R 다이어그램에서 선(링크) — 개체 타입과 속성, 개체 타입과 관계 타입을 연결
- Q: E-R 다이어그램에서 밑줄 그은 타원 — 기본키 속성

## 논리적 데이터 모델

- **관계 데이터 모델 (Relational Data Model)** — 데이터를 행과 열로 된 2차원 테이블로 표현하고 테이블 사이의 관계를 공통 속성(키)으로 나타내는 모델. 1:1, 1:N, N:M을 모두 표현한다
- **계층 데이터 모델 (Hierarchical Data Model)** — 데이터를 부모-자식의 트리 구조로 표현하는 모델. 1:N 관계만 허용하며 N:M은 직접 표현하지 못한다
  - 대표 DBMS: IMS
- **네트워크 데이터 모델 (Network Data Model)** — 데이터를 그래프 구조로 표현하고 오너-멤버 관계로 연결하는 모델. CODASYL이 표준을 제안했다
  - 망 데이터 모델이라고도 하며 대표 DBMS는 IDS

## 데이터 모델 품질 기준 (정완준최일활)

- **정확성 (Accuracy)** — 모델이 표기법에 맞게 그려졌고 업무 요구사항과 업무 규칙을 틀림없이 담고 있는지를 보는 기준
- **완전성 (Completeness)** — 필요한 개체·속성·관계와 요구사항이 빠짐없이 모델에 들어갔는지를 보는 기준
- **준거성 (Compliance)** — 데이터 표준, 명명 규칙, 관련 법령 등 정해진 규칙을 지켜 작성했는지를 보는 기준
- **최신성 (Up-to-date)** — 모델이 현재 운영 중인 시스템의 최근 상태와 새로 생긴 변경 사항을 바로 반영하고 있는지를 보는 기준
- **일관성 (Consistency)** — 여러 업무에서 함께 쓰는 데이터를 한 번만 정의하고 모든 곳이 그 정의를 똑같이 참조하는지를 보는 기준
- **활용성 (Usability)** — 모델과 그 설명이 사용자가 충분히 이해할 수 있고, 업무가 바뀌어도 크게 손대지 않고 쓸 수 있는지를 보는 기준

## 릴레이션 구조

- **튜플 (Tuple)** — 테이블의 한 행에 해당하며 서로 관련된 속성 값들의 모임. 파일 구조의 레코드에 대응한다
- **속성 (Attribute)** — 테이블의 한 열에 해당하며 개체의 특성을 나타내는 가장 작은 논리적 단위. 파일 구조의 필드에 대응한다
  - 애트리뷰트
- **도메인 (Domain)** — 한 속성이 가질 수 있는, 같은 타입의 원자값 전체 집합. 그 속성에 들어갈 수 있는 값의 범위를 정한다
  - 예: 성별 → {남, 여}
- **카디널리티 (Cardinality)** — 한 테이블에 들어 있는 행(튜플)의 수. 행이 추가·삭제될 때마다 바뀐다
  - 기수라고도 한다
- **차수 (Degree)** — 한 테이블을 구성하는 열(속성)의 수. 테이블 구조를 바꾸지 않는 한 고정된다
  - 디그리

## 키

- **슈퍼키 (Super Key)** — 행을 하나로 짚어 낼 수 있는 속성 묶음이면 무엇이든 해당하는 키. 군더더기 속성이 섞여 있어도 되므로, 여기서 불필요한 속성을 덜어 내면 후보키가 된다
- **후보키 (Candidate Key)** — 행을 유일하게 구별할 수 있는 속성 조합 가운데 유일성과 최소성을 모두 만족하는 것
- **기본키 (Primary Key)** — 여러 후보키 중에서 대표 식별자로 고른 키. NULL과 중복 값을 가질 수 없다
- **대체키 (Alternate Key)** — 후보키가 둘 이상일 때 기본키로 선택되지 않고 남은 나머지 후보키
  - 보조키라고도 한다
- **외래키 (Foreign Key)** — 다른 테이블의 기본키를 참조하는 속성. 테이블 간 관계를 표현하며 값은 NULL이거나 참조 대상에 실제로 있는 값이어야 한다
- **일반 속성 (Non-key Attribute)** — 어떤 후보키에도 포함되지 않는 속성. 정규화에서 키에 종속되는 쪽으로 다뤄진다

## 무결성

- **무결성 (Integrity)** — 저장된 데이터 값이 그것이 나타내는 현실 세계의 실제 값과 일치하도록 정확성을 보장하는 성질
- **개체 무결성 (Entity Integrity)** — 기본키를 구성하는 어떤 속성도 NULL이나 중복 값을 가질 수 없다는 제약
- **참조 무결성 (Referential Integrity)** — 외래키 값은 NULL이거나 참조하는 테이블의 기본키 값 중 하나와 같아야 한다는 제약
- **도메인 무결성 (Domain Integrity)** — 각 속성 값은 그 속성에 정해진 데이터 타입·허용 범위·형식 안에 있어야 한다는 제약
- **고유 무결성 (Unique Integrity)** — UNIQUE로 지정된 속성은 테이블 안에서 서로 다른 값을 가져야 한다는 제약

## 함수 종속

- **함수 종속 (Functional Dependency)** — 속성 X의 각 값에 대해 속성 Y의 값이 항상 하나로 정해지는 관계. X를 결정자, Y를 종속자라 하고 X → Y로 쓴다
- **부분 함수 종속 (Partial Functional Dependency)** — 기본키가 여러 속성으로 이루어졌을 때 어떤 속성이 기본키 전체가 아니라 그 일부에만 종속되는 관계. 2NF에서 제거한다
- **이행적 함수 종속 (Transitive Functional Dependency)** — A → B이고 B → C일 때 A → C가 성립하는 관계. 3NF에서 제거한다
- **이상 현상 (Anomaly)** — 정규화되지 않은 테이블에서 데이터 중복 때문에 삽입·삭제·갱신할 때 예상하지 못한 문제가 생기는 현상

## 이상 현상의 종류 (삽삭갱)

- **삽입 이상 (Insertion Anomaly)** — 데이터를 넣을 때 원하지 않는 값까지 같이 넣어야 하거나, 일부 값이 없어 아예 넣을 수 없는 현상
- **삭제 이상 (Deletion Anomaly)** — 한 행을 지울 때 남겨야 할 다른 정보까지 함께 사라지는 연쇄 손실 현상
- **갱신 이상 (Update Anomaly)** — 중복 저장된 값 중 일부만 바뀌어 같은 사실이 서로 다른 값으로 남는 불일치 현상

## 정규화

- **정규화 (Normalization)** — 테이블을 함수 종속에 따라 정보 손실 없이 분해해 중복을 줄이고 이상 현상을 없애는 과정
- **제1정규형 (1NF)** — 모든 속성의 도메인이 더 쪼갤 수 없는 원자값으로만 이루어진 상태. 반복 그룹을 없앤다
- **제2정규형 (2NF)** — 1NF를 만족하면서 키가 아닌 모든 속성이 기본키 전체에 완전 함수 종속인 상태. 부분 함수 종속을 없앤다
- **제3정규형 (3NF)** — 2NF를 만족하면서 키가 아닌 속성들 사이의 이행적 함수 종속을 없앤 상태
- **BCNF (Boyce-Codd Normal Form)** — 3NF를 만족하면서 모든 결정자가 후보키인 상태. 후보키가 아닌 결정자를 없앤다
- **제4정규형 (4NF)** — BCNF를 만족하면서 다치 종속(MVD, Multi-Valued Dependency)을 없앤 상태
- **제5정규형 (5NF)** — 4NF를 만족하면서 모든 조인 종속이 후보키를 통해서만 성립하도록 조인 종속을 없앤 상태
  - PJ/NF(Projection-Join Normal Form)라고도 한다
- Q: 정규화 단계별 제거 대상 — 1NF 원자값 아닌 도메인 → 2NF 부분 함수 종속 → 3NF 이행적 함수 종속 → BCNF 후보키가 아닌 결정자 → 4NF 다치 종속 → 5NF 조인 종속

## 반정규화

- **반정규화 (Denormalization)** — 정규화된 모델을 조회 성능과 개발 편의를 위해 일부러 통합·중복·분리하는 과정. 일관성과 무결성이 깨질 위험을 감수한다
  - 역정규화라고도 한다
- Q: 반정규화 기법 4가지 — 테이블 통합, 테이블 분할, 중복 테이블 추가, 중복 속성 추가
- **집계 테이블 (Aggregation Table)** — 합계·평균 같은 통계 값을 미리 계산해 담아 두고, 원본이 바뀔 때 트리거로 함께 갱신하는 추가 테이블
  - 통계 테이블이라고도 한다
- **진행 테이블 (Progress Table)** — 다대다 관계인 두 테이블 사이의 진행 상태를 빠르게 조회하려고 두는 추가 테이블. 데이터 양과 사용 빈도를 따져 기본키를 정한다
- **특정 부분만 포함하는 테이블** — 원본 테이블에서 자주 쓰는 일부 컬럼이나 행만 골라 따로 만든 추가 테이블
- **중복 테이블 (Duplicated Table)** — 다른 서버나 업무의 테이블과 같은 구조·데이터를 복사해 두어 원격 조인이나 반복 접근을 줄이는 추가 테이블

## 관계 대수·해석

- **관계 대수 (Relational Algebra)** — 원하는 결과를 얻으려면 어떤 연산을 어떤 순서로 수행할지를 명시하는 절차적 언어
- **관계 해석 (Relational Calculus)** — 원하는 결과가 무엇인지만 정의하고 처리 순서는 명시하지 않는 비절차적 언어. 프레디킷 해석에 기반하며 튜플 해석과 도메인 해석이 있다
  - 코드(E. F. Codd)가 제안
- Q: SELECT 연산의 기호와 의미 — σ (시그마) — 조건을 만족하는 행(튜플)만 골라내는 수평 연산
- Q: PROJECT 연산의 기호와 의미 — π (파이) — 지정한 속성(열)만 뽑아내는 수직 연산
- Q: JOIN 연산의 기호와 의미 — ⋈ — 공통 속성을 기준으로 두 릴레이션을 하나로 합치는 연산
- Q: DIVISION 연산의 기호와 의미 — ÷ — R ÷ S: S의 모든 튜플과 관련된 R의 튜플을 S의 속성을 뺀 채 구하는 연산
- Q: 합집합·교집합·차집합의 기호 — ∪ (합집합), ∩ (교집합), − (차집합)
- Q: 카티션 프로덕트 기호와 결과 크기 — × — 차수는 두 릴레이션 차수의 합, 카디널리티는 두 릴레이션 카디널리티의 곱

## 트랜잭션 상태

- **트랜잭션 (Transaction)** — 데이터베이스 상태를 바꾸기 위해 한꺼번에 수행되어야 하는 일련의 연산 묶음. 병행 제어와 회복의 기본 단위다
- **활동 (Active)** — 트랜잭션이 시작되어 연산을 정상적으로 실행하고 있는 상태
- **부분 완료 (Partially Committed)** — 마지막 연산까지 실행을 마쳤지만 아직 Commit은 하지 않은 상태
- **완료 (Committed)** — 실행을 성공적으로 끝내고 Commit 연산까지 수행한 상태
- **실패 (Failed)** — 실행 중 오류가 발생해 더 이상 정상적으로 진행할 수 없게 된 상태
- **철회 (Aborted)** — 실행에 실패해 Rollback을 수행하고 시작 전 상태로 되돌아간 상태

## 트랜잭션 특성 ACID (원일격지)

- **원자성 (Atomicity)** — 연산 전체가 모두 반영되거나 하나도 반영되지 않아야 하는 성질(All or Nothing). Commit과 Rollback으로 보장한다
- **일관성 (Consistency)** — 실행을 성공적으로 마치면 무결성 제약 등 정해진 규칙을 계속 만족해 모순 없는 상태가 유지되어야 하는 성질
- **격리성 (Isolation)** — 둘 이상이 동시에 실행될 때 한쪽이 끝나기 전에는 다른 쪽이 그 중간 결과를 보거나 끼어들 수 없어야 하는 성질
- **지속성 (Durability)** — 성공적으로 완료된 결과는 이후 시스템 장애가 나더라도 영구히 보존되어야 하는 성질

## 병행 제어

- **병행 제어 (Concurrency Control)** — 여러 트랜잭션이 동시에 실행될 때 데이터의 일관성이 깨지지 않도록 실행 순서와 접근을 조정하는 기법

## 병행 제어를 하지 않을 때의 문제 (갱현모연)

- **갱신 손실 (Lost Update)** — 두 트랜잭션이 같은 데이터를 동시에 고칠 때 한쪽의 수정 결과가 다른 쪽에 덮어써져 사라지는 문제
- **현황 파악 오류 (Dirty Read)** — 다른 트랜잭션이 아직 확정하지 않은 중간 결과를 읽어 잘못된 값을 참조하는 문제
- **모순성 (Inconsistency)** — 한 트랜잭션이 여러 값을 읽는 사이 다른 트랜잭션이 그 값들을 바꿔, 서로 맞지 않는 값들로 처리하게 되는 문제
- **연쇄 복귀 (Cascading Rollback)** — 트랜잭션 하나가 철회될 때 그 결과를 이미 읽어 간 다른 트랜잭션까지 줄줄이 함께 취소되어야 하는 문제

## 병행 제어 기법

- **로킹 (Locking)** — 트랜잭션이 쓰려는 데이터의 접근 권한을 독점하고 다 쓴 뒤 풀어 주어 다른 트랜잭션의 동시 접근을 막는 기법
- Q: 로킹 단위가 커지면 / 작아지면 — 커지면 로크 수가 줄어 관리가 쉽지만 병행성이 낮아진다
  - 작아지면 병행성은 높아지지만 관리 오버헤드가 커진다
- **2단계 로킹 (Two-Phase Locking)** — 모든 트랜잭션이 로크 획득만 하는 확장 단계와 해제만 하는 축소 단계를 거치도록 해 직렬 가능성을 보장하는 규약. 교착 상태는 막지 못한다
- **타임스탬프 순서 (Timestamp Ordering)** — 트랜잭션이 시작될 때 고유한 시각값을 부여하고, 그 값이 작은 쪽이 먼저 실행된 것처럼 접근 순서를 강제하는 기법. 교착 상태가 생기지 않는다
- **낙관적 검증 (Optimistic Validation)** — 트랜잭션 수행 중에는 아무 검사도 하지 않다가 끝날 때 한 번에 충돌 여부를 확인해, 문제가 있으면 철회하는 기법

## 회복 기법

- Q: 로그를 보고 완료된 트랜잭션의 변경을 다시 적용하는 회복 연산 — Redo (재실행)
- Q: 로그를 보고 완료되지 못한 트랜잭션의 변경을 취소하는 회복 연산 — Undo (취소)
- **즉시 갱신 (Immediate Update)** — 트랜잭션 수행 중 변경 내용을 Commit 전에도 곧바로 데이터베이스에 반영하는 회복 기법. 장애 시 로그로 Redo와 Undo를 모두 수행한다
- **지연 갱신 (Deferred Update)** — 부분 완료될 때까지 변경 내용을 로그에만 적어 두었다가 완료 후 데이터베이스에 반영하는 회복 기법. 장애 시 Undo 없이 Redo만 한다
- **검사점 회복 (Checkpoint Recovery)** — 일정 간격으로 그 시점의 상태를 로그에 표시해 두고, 장애가 나면 그 표시 이후 기록만 살펴 Redo·Undo 범위를 줄이는 회복 기법
- **그림자 페이징 (Shadow Paging)** — 트랜잭션 시작 시 페이지 테이블 사본을 따로 보관하고 변경은 새 페이지에 기록하다가, 장애가 나면 보관한 사본으로 되돌리는 회복 기법. 로그가 필요 없다

## 인덱스·뷰

- **인덱스 (Index)** — 키 값과 그 행이 저장된 위치를 쌍으로 보관해 검색 속도를 높이는 자료 구조. 주로 B-트리로 구현하며 잦은 삽입·삭제에는 부담이 된다
- **클러스터드 인덱스 (Clustered Index)** — 테이블의 행 자체가 키 순서대로 물리적으로 정렬되어 저장되는 방식. 테이블당 하나만 만들 수 있고 범위 검색에 유리하다
- **넌클러스터드 인덱스 (Non-Clustered Index)** — 행의 물리적 순서는 그대로 두고 키와 행 위치(포인터)만 별도 구조에 정렬해 두는 방식. 테이블당 여러 개 만들 수 있다
- **뷰 (View)** — 하나 이상의 기본 테이블에서 유도한 이름 있는 가상 테이블. 물리적으로 저장되지 않으며 정의를 ALTER로 바꿀 수 없어 삭제 후 다시 만든다
- **옵티마이저 (Optimizer)** — SQL 문을 가장 효율적으로 처리할 실행 계획을 찾아 주는 DBMS 내부 엔진. 규칙 기반(RBO)과 비용 기반(CBO)이 있다
- Q: SQL 처리 흐름 3단계 — 구문 분석(Parse) → 실행(Execute) → 인출(Fetch)

## 분산 데이터베이스

- **분산 데이터베이스 (Distributed Database)** — 논리적으로는 하나의 시스템이지만 데이터가 네트워크로 연결된 여러 사이트에 물리적으로 흩어져 저장·관리되는 구조

## 분산 데이터베이스의 투명성 (위분중병장)

- **위치 투명성 (Location Transparency)** — 데이터가 실제로 어느 사이트에 있는지 몰라도 논리적인 이름만으로 접근할 수 있는 성질
- **분할 투명성 (Fragmentation Transparency)** — 하나의 논리적 테이블이 여러 조각으로 나뉘어 여러 곳에 저장되어 있어도 사용자는 그 사실을 의식하지 않는 성질
- **중복 투명성 (Replication Transparency)** — 같은 데이터가 여러 사이트에 복제되어 있어도 사용자는 하나만 있는 것처럼 쓸 수 있는 성질
- **병행 투명성 (Concurrency Transparency)** — 여러 트랜잭션이 동시에 실행되어도 그 결과가 서로 영향받지 않고 일관되게 유지되는 성질
- **장애 투명성 (Failure Transparency)** — 일부 사이트나 통신망에 고장이 나도 트랜잭션을 정확하게 처리해 내는 성질

## 이중화

- **데이터베이스 이중화 (Database Replication)** — 장애에 대비해 같은 데이터를 둘 이상의 데이터베이스에 복제해 두고, 한쪽의 변경을 다른 쪽에도 반영해 함께 유지하는 기법
- **Eager 기법** — 한쪽에서 데이터가 바뀌면 트랜잭션 수행 도중 곧바로 모든 복제본에 반영하는 이중화 방식
- **Lazy 기법** — 트랜잭션이 끝난 뒤 별도의 새 트랜잭션을 만들어 변경 내용을 다른 복제본에 전달하는 이중화 방식. 잠시 불일치가 생길 수 있다

## 파티셔닝

- **파티셔닝 (Partitioning)** — 큰 테이블이나 인덱스를 관리하기 쉬운 작은 단위로 나누어 저장해 성능과 가용성을 높이는 기법
- Q: 파티셔닝 종류 — 범위(Range), 해시(Hash), 목록(List), 조합(Composite)
- **수평 분할 (Horizontal Partitioning)** — 같은 컬럼 구조를 유지한 채 행 단위로 테이블을 여러 조각으로 나누는 방식
  - 예: 지역별로 고객 행을 서로 다른 파티션에 저장
- **수직 분할 (Vertical Partitioning)** — 열 단위로 테이블을 나누는 방식. 자주 쓰는 컬럼과 드물게 쓰는 컬럼을 따로 저장한다

## 튜닝

- **튜닝 (Tuning)** — SQL 문, 인덱스, 메모리·디스크 설정 등을 조정해 처리 속도를 높이고 자원을 효율적으로 쓰도록 개선하는 활동
