# 소프트웨어 설계 · 객체지향 · UML

## 결합도·응집도 순서

- Q: 결합도 순서 (강함 → 약함) — 내용 → 공통 → 외부 → 제어 → 스탬프 → 자료
- Q: 응집도 순서 (약함 → 강함) — 우연적 → 논리적 → 시간적 → 절차적 → 통신적 → 순차적 → 기능적

> 결합도는 낮을수록, 응집도는 높을수록 좋은 설계다.

## 결합도 종류 (내공외제스자)

- **내용 결합도 (Content Coupling)** — 한 모듈이 다른 모듈의 내부 변수나 코드를 직접 참조하거나 고치는, 가장 강한 의존 형태.
- **공통 결합도 (Common Coupling)** — 여러 모듈이 하나의 전역 변수나 공유 데이터 영역을 함께 읽고 쓰는 형태.
  - 그 영역을 한 번 고치면 쓰는 모듈 전부가 영향을 받는다
- **외부 결합도 (External Coupling)** — 어떤 모듈이 선언한 데이터(변수)를 다른 모듈이 가져다 참조하는 형태.
  - 전역 영역 전체가 아니라 특정 선언 데이터만 공유한다
- **제어 결합도 (Control Coupling)** — 한 모듈이 플래그 같은 신호를 넘겨 다른 모듈의 내부 처리 흐름을 결정하는 형태.
  - 제어 정보가 거꾸로 흘러 호출 관계가 뒤집히는 권리 전도가 생길 수 있다
- **스탬프 결합도 (Stamp Coupling)** — 모듈 사이에 배열·레코드 같은 자료 구조를 통째로 넘기고, 받는 쪽은 그 일부만 쓰는 형태.
  - 구조가 바뀌면 해당 필드를 안 쓰는 모듈도 영향을 받는다
- **자료 결합도 (Data Coupling)** — 모듈끼리 꼭 필요한 값만 매개변수로 주고받는, 가장 약하고 바람직한 형태.

## 응집도 종류 (우논시절통순기)

- **우연적 응집도 (Coincidental Cohesion)** — 서로 아무 관련 없는 처리들이 별다른 이유 없이 한 모듈에 모여 있는, 가장 약한 형태.
- **논리적 응집도 (Logical Cohesion)** — 성격이 비슷해 같은 범주로 볼 수 있는 처리들을 한 모듈에 넣고, 플래그로 골라 실행하는 형태.
  - 예: 장치별 입력 루틴을 한 모듈에 모아 둔 경우
- **시간적 응집도 (Temporal Cohesion)** — 초기화·종료 처리처럼 같은 시점에 실행된다는 이유 하나로 묶인 형태.
- **절차적 응집도 (Procedural Cohesion)** — 정해진 순서대로 수행된다는 이유로 묶였지만, 요소끼리 데이터를 넘겨주지는 않는 형태.
- **통신적 응집도 (Communicational Cohesion)** — 같은 입력 데이터를 쓰거나 같은 출력 데이터를 만드는 서로 다른 처리들을 한 모듈로 묶은 형태.
- **순차적 응집도 (Sequential Cohesion)** — 한 요소의 출력이 곧바로 다음 요소의 입력이 되는 처리들을 한 모듈로 묶은 형태.
- **기능적 응집도 (Functional Cohesion)** — 모듈 안의 모든 요소가 하나의 명확한 일을 위해 협력하는, 가장 강하고 바람직한 형태.

## 객체지향 특징

- **캡슐화 (Encapsulation)** — 데이터(속성)와 그 데이터를 다루는 연산(메서드)을 하나의 단위로 묶어 다루는 것.
  - 변경의 파급을 줄이고 재사용을 쉽게 한다
- **정보 은닉 (Information Hiding)** — 객체의 내부 구현은 감추고 공개된 인터페이스로만 접근하게 해, 내부를 바꿔도 외부에 영향이 퍼지지 않게 하는 원리.
- **상속 (Inheritance)** — 상위 클래스의 속성과 연산을 하위 클래스가 물려받아 그대로 쓰거나 확장하는 것.
- **다형성 (Polymorphism)** — 같은 이름의 메시지를 받아도 객체마다 자기 방식으로 다르게 응답하는 성질.
  - 오버로딩·오버라이딩으로 구현
- **추상화 (Abstraction)** — 복잡한 대상에서 문제와 상관없는 세부는 덜어 내고 핵심 특징만 뽑아 모델로 나타내는 것.
  - 종류: 기능·자료·제어

## 객체지향 설계 원칙 (SOLID) (SOLID)

- **SRP (Single Responsibility Principle)** — 하나의 클래스는 한 가지 책임만 지고, 바뀌어야 할 이유도 하나뿐이어야 한다는 원칙.
- **OCP (Open-Closed Principle)** — 새 기능을 덧붙이는 확장은 허용하되, 이미 동작하는 기존 코드는 고치지 않아도 되도록 설계해야 한다는 원칙.
- **LSP (Liskov Substitution Principle)** — 하위 타입 객체를 상위 타입 객체 자리에 넣어도 프로그램이 올바르게 동작해야 한다는 원칙.
- **ISP (Interface Segregation Principle)** — 클라이언트가 쓰지 않는 메서드에 의존하지 않도록, 범용 메서드 묶음 하나를 역할별 작은 묶음 여러 개로 쪼개야 한다는 원칙.
- **DIP (Dependency Inversion Principle)** — 상위 모듈과 하위 모듈 모두 구체 구현이 아니라 추상 타입에 기대야 한다는 원칙.
  - 참조 방향: 구체 클래스 → 인터페이스·추상 클래스

## 럼바우 (Rumbaugh) 객체지향 분석 기법 (객동기)

- **객체 모델링 (Object Modeling)** — 시스템의 구성 요소와 그 속성·관계를 찾아 정적 구조도(객체 다이어그램)로 표현하는 첫 단계.
  - 정보 모델링이라고도 한다
- **동적 모델링 (Dynamic Modeling)** — 시간 흐름에 따라 객체가 겪는 상태 변화와 제어 흐름을 상태 다이어그램으로 표현하는 단계.
- **기능 모델링 (Functional Modeling)** — 입력이 어떤 처리를 거쳐 출력으로 바뀌는지 자료 흐름도(DFD)로 표현하는 단계.

> 수행 순서: 객체 → 동적 → 기능 (그룹 앞글자 순서 그대로)

## 기타 객체지향 분석 방법론

- **부치 (Booch) 방법** — 미시적·거시적 개발 프로세스를 모두 쓰며 클래스와 객체를 식별하고 그 속성·연산을 정의해 나가는 방법.
- **코드-요든 (Coad-Yourdon) 방법** — E-R 다이어그램을 써서 객체의 행위를 모델링하고, 객체·구조·주제·속성·연산 순으로 식별해 나가는 방법.
- **야콥슨 (Jacobson) 방법** — 유스케이스를 중심에 두고 사용자와 시스템의 상호작용을 따라가며 분석하는 방법.
  - OOSE
- **워프스-브록 (Wirfs-Brock) 방법** — 분석과 설계를 따로 나누지 않고, 고객 명세서를 평가하는 일부터 설계까지 이어서 진행하는 방법.

## 디자인 패턴 분류 (GoF)

- **생성 패턴 (Creational Pattern)** — 객체를 만드는 과정을 캡슐화해, 무엇을 어떻게 만들지를 사용하는 코드로부터 떼어 내는 패턴 묶음.
- **구조 패턴 (Structural Pattern)** — 클래스나 객체를 조합해 더 큰 구성을 만드는 방법을 다루는 패턴 묶음.
- **행위 패턴 (Behavioral Pattern)** — 객체 사이의 책임 분배와 상호작용, 알고리즘의 흐름을 다루는 패턴 묶음.
- Q: 생성 패턴 5가지 — Builder, Prototype, Factory Method, Abstract Factory, Singleton
- Q: 구조 패턴 7가지 — Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy
- Q: 행위 패턴 11가지 — Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor

> GoF 23개 = 생성 5 + 구조 7 + 행위 11

## 생성 패턴

- **빌더 (Builder)** — 복잡한 객체를 만드는 단계를 분리해, 같은 조립 절차로 서로 다른 표현의 결과물을 얻게 하는 패턴.
  - 부품을 하나씩 끼워 완성품을 만드는 방식
- **프로토타입 (Prototype)** — 새로 만드는 대신 이미 만들어 둔 객체를 복사(clone)해서 새 객체를 얻는 패턴.
  - 만드는 비용이 큰 객체를 매번 처음부터 만들지 않아도 된다
- **팩토리 메서드 (Factory Method)** — 객체를 만드는 인터페이스는 상위 클래스가 정하고, 어떤 클래스의 인스턴스를 만들지는 하위 클래스가 정하게 하는 패턴.
  - 가상 생성자(Virtual Constructor)라고도 한다
- **추상 팩토리 (Abstract Factory)** — 구체 클래스를 지정하지 않고, 서로 관련된 객체들의 제품군을 한꺼번에 만들 수 있는 인터페이스를 제공하는 패턴.
- **싱글톤 (Singleton)** — 어떤 클래스의 인스턴스가 오직 하나만 만들어지도록 보장하고, 어디서든 그 하나에 접근할 통로를 주는 패턴.

## 구조 패턴

- **어댑터 (Adapter)** — 호환되지 않는 인터페이스를 가진 클래스를 감싸, 클라이언트가 기대하는 인터페이스로 바꿔 주는 패턴.
  - 110V ↔ 220V 변환 플러그
- **브리지 (Bridge)** — 기능 계층과 구현 계층을 분리해, 두 계층이 서로 독립적으로 확장될 수 있게 하는 패턴.
- **컴포지트 (Composite)** — 단일 객체와 여러 객체를 담은 그릇 객체를 트리로 구성해, 클라이언트가 둘을 똑같이 다루게 하는 패턴.
  - 파일과 폴더의 관계
- **데코레이터 (Decorator)** — 기존 객체를 겹겹이 감싸, 상속 없이 실행 중에 새 기능(책임)을 덧붙이는 패턴.
- **퍼사드 (Facade)** — 복잡한 서브시스템 앞에 단순한 통합 창구 하나를 두어, 클라이언트가 내부를 몰라도 쓸 수 있게 하는 패턴.
- **플라이웨이트 (Flyweight)** — 여러 객체가 공통으로 갖는 상태를 공유해 인스턴스 수와 메모리 사용을 줄이는 패턴.
- **프록시 (Proxy)** — 실제 객체 앞에 대리 객체를 두어 접근 제어·지연 로딩·원격 접근 같은 일을 대신 처리하게 하는 패턴.

## 행위 패턴

- **책임 연쇄 (Chain of Responsibility)** — 요청을 처리할 수 있는 객체들을 사슬처럼 이어, 처리할 객체가 나올 때까지 요청을 차례로 넘기는 패턴.
- **커맨드 (Command)** — 요청 자체를 객체로 캡슐화해, 요청을 매개변수화·대기열·기록할 수 있고 실행 취소(undo)도 가능하게 하는 패턴.
- **인터프리터 (Interpreter)** — 간단한 언어의 문법 규칙을 클래스 계층으로 표현하고, 이를 이용해 문장을 평가·실행하는 패턴.
  - 예: SQL·정규식 처리기
- **이터레이터 (Iterator)** — 컬렉션의 내부 표현을 드러내지 않고 그 원소들에 하나씩 차례로 접근하는 방법을 제공하는 패턴.
- **미디에이터 (Mediator)** — 여러 객체가 서로 직접 참조하지 않고 중재 객체를 거쳐 소통하게 해 객체 간 결합을 줄이는 패턴.
- **메멘토 (Memento)** — 캡슐화를 깨지 않고 객체의 내부 상태를 저장해 두었다가 나중에 그 상태로 되돌릴 수 있게 하는 패턴.
  - 예: Ctrl+Z
- **옵저버 (Observer)** — 한 객체의 상태가 바뀌면 그 객체를 지켜보는 다른 객체들에게 자동으로 알림이 가고 갱신되는 일대다 의존 패턴.
- **스테이트 (State)** — 객체의 내부 모드(예: 대기·실행·정지)마다 행동을 별도 클래스로 나눠, 모드가 바뀌면 같은 호출도 다르게 동작하게 하는 패턴.
- **스트래티지 (Strategy)** — 같은 문제를 푸는 여러 알고리즘을 각각 캡슐화해 서로 바꿔 끼울 수 있게 하고, 실행 중에 골라 쓰게 하는 패턴.
- **템플릿 메서드 (Template Method)** — 상위 클래스가 알고리즘의 골격(처리 순서)을 정해 두고, 세부 단계 일부를 하위 클래스가 재정의하게 하는 패턴.
- **비지터 (Visitor)** — 데이터 구조와 그 위에서 수행할 연산을 분리해, 구조를 바꾸지 않고 새 연산을 추가할 수 있게 하는 패턴.
  - 각 원소가 연산 객체를 받아들여(accept) 처리를 맡긴다

## UML 구조 다이어그램 (정적)

- **클래스 다이어그램 (Class Diagram)** — 시스템을 이루는 클래스의 속성·연산과 그 사이의 관계를 그려 정적 구조를 보여 주는 다이어그램.
- **객체 다이어그램 (Object Diagram)** — 특정 시점에 실제로 존재하는 인스턴스들과 그 사이의 링크를 스냅숏처럼 표현하는 다이어그램.
- **패키지 다이어그램 (Package Diagram)** — 관련 모델 요소들을 묶음 단위로 그룹화하고, 묶음 사이의 의존 관계를 표현하는 다이어그램.
- **컴포넌트 다이어그램 (Component Diagram)** — 구현 단계에서 교체 가능한 소프트웨어 부품들과 그 사이의 인터페이스·의존 관계를 표현하는 다이어그램.
- **배치 다이어그램 (Deployment Diagram)** — 하드웨어 노드(서버·장치)와 그 위에 올라가는 산출물, 노드 간 통신 경로를 표현하는 물리적 다이어그램.
- **복합체 구조 다이어그램 (Composite Structure Diagram)** — 클래스나 컴포넌트의 내부 구조를 파트·포트·연결자로 자세히 표현하는 다이어그램.

## 클래스 다이어그램 구성요소

- Q: 클래스 표기의 세 칸 (위 → 아래) — 이름 → 속성 → 연산(메서드)
- **속성 (Attribute)** — 클래스가 가지는 데이터로, 각 객체의 성질이나 현재 값을 나타내는 구성 요소.
  - 표기 예: `- name: String`
- **연산 (Operation)** — 클래스가 외부 요청을 받아 수행할 수 있는 동작으로, 코드로 구현하면 메서드가 되는 것.
  - 표기 예: `+ getName(): String`
- **접근 제어자 (Access Modifier)** — 속성·연산 이름 앞에 기호를 붙여, 외부에서 접근할 수 있는 범위를 나타내는 것.
- Q: UML 접근 제어자 기호 `+` `#` `~` `-` — `+` public · `#` protected · `~` package(default) · `-` private

## UML 행위 다이어그램 (동적)

- **유스케이스 다이어그램 (Use Case Diagram)** — 사용자(액터) 관점에서 시스템이 제공하는 기능과 액터의 관계를 그려 요구사항을 정리하는 다이어그램.
  - 관계: 포함(include)·확장(extend)·일반화
- **활동 다이어그램 (Activity Diagram)** — 처리 흐름을 단계별 동작과 분기·병렬 흐름으로 그려 업무나 알고리즘의 진행을 보여 주는 다이어그램.
  - 순서도와 비슷하다
- **상태 다이어그램 (State Diagram)** — 한 객체가 이벤트를 받을 때마다 어떤 조건에서 어떤 조건으로 전이하는지 표현하는 다이어그램.
  - 럼바우 동적 모델링에 쓰인다
- **순서 다이어그램 (Sequence Diagram)** — 객체들이 주고받는 메시지를 위에서 아래로 흐르는 시간 축에 따라 표현하는 다이어그램.
  - 구성: 액터·객체·생명선·실행(활성) 상자·메시지
- **커뮤니케이션 다이어그램 (Communication Diagram)** — 객체 간 메시지 교환을 그리되, 시간 순서보다 객체 사이의 연결(링크) 관계에 초점을 둔 다이어그램.
  - 옛 이름: 협업(Collaboration) 다이어그램
- **타이밍 다이어그램 (Timing Diagram)** — 객체의 조건 변화를 정확한 시간 축 위에 그려 시간 제약을 드러내는 다이어그램.
- **상호작용 개요 다이어그램 (Interaction Overview Diagram)** — 여러 순서·커뮤니케이션 다이어그램 조각을 활동 다이어그램처럼 이어 전체 제어 흐름을 한눈에 보여 주는 다이어그램.

## 활동 다이어그램 요소

- **포크 노드 (Fork Node)** — 하나의 흐름을 여러 개의 병렬 흐름으로 나누는 지점으로, 굵은 막대로 그린다.
- **조인 노드 (Join Node)** — 병렬로 갈라졌던 여러 흐름을 다시 하나로 합치는 지점으로, 굵은 막대로 그린다.
- **결정(조건) 노드 (Decision Node)** — 조건에 따라 흐름이 여러 갈래 중 하나로 나뉘는 지점으로, 마름모로 그린다.
- **병합 노드 (Merge Node)** — 조건 분기로 갈라졌던 흐름들을 다시 하나로 모으는 지점으로, 마름모로 그린다.
- **구획면 (Swimlane)** — 활동을 수행 주체(부서·역할)별로 나눠 보이게 하려고 그은 가로 또는 세로 구역.

## UML 관계

- **연관 관계 (Association)** — 두 사물이 서로 의미 있게 관련되어 있어 한쪽이 다른 쪽을 알고 있음을 실선으로 잇는 관계.
  - 방향이 있으면 화살표, 양 끝에 다중도 표기
- **집합(집약) 관계 (Aggregation)** — 전체와 부분의 관계이지만 부분이 전체 없이도 독립적으로 존재할 수 있는 관계.
  - 전체 쪽에 속이 빈 마름모
- **포함(합성) 관계 (Composition)** — 부분이 전체에 종속되어 전체가 사라지면 부분도 함께 사라지는 강한 전체-부분 관계.
  - 전체 쪽에 속이 채워진 마름모
- **일반화 관계 (Generalization)** — 한 사물이 다른 사물보다 더 포괄적인 개념이어서 상위·하위로 나뉘는 is-a 관계.
  - 하위 → 상위로 속이 빈 삼각형 화살표 실선
- **실체화 관계 (Realization)** — 인터페이스가 정해 둔 기능을 클래스가 실제로 구현해 내는 관계.
  - 속이 빈 삼각형 화살표 점선
- **의존 관계 (Dependency)** — 한 사물이 다른 사물을 잠깐 사용하는 짧은 관계로, 상대가 바뀌면 영향을 받는 관계.
  - 점선 화살표

## 단위 모듈 작성 원칙 (정명완일추)

- **정확성 (Correctness)** — 모듈이 실제로 필요한 기능을 요구한 대로 틀림없이 수행하도록 작성해야 한다는 원칙.
- **명확성 (Clarity)** — 코드를 읽는 누구나 같은 의미로 이해할 수 있도록 모호함 없이 작성해야 한다는 원칙.
- **완전성 (Completeness)** — 모듈이 동작하는 데 필요한 요소와 처리를 하나도 빠뜨리지 않고 작성해야 한다는 원칙.
- **일관성 (Consistency)** — 공통 코드와 표기·작성 방식을 모듈 전반에 같은 규칙으로 적용해야 한다는 원칙.
- **추적성 (Traceability)** — 각 모듈이 어떤 요구사항에서 나왔고 다른 모듈과 어떻게 이어지는지 따라갈 수 있게 작성해야 한다는 원칙.

## 모듈 구조 지표

- **팬인 (Fan-In)** — 시스템 구조도에서 어떤 모듈을 호출하는 상위 모듈의 수. 즉 그 모듈로 제어가 들어오는 갈래 수이고, 값이 크면 여러 곳에서 재사용되는 공통 모듈이다
- **팬아웃 (Fan-Out)** — 어떤 모듈이 직접 호출하는 하위 모듈의 수. 값이 지나치게 크면 그 모듈이 너무 많은 일을 떠맡아 복잡도가 높다는 신호다

> 좋은 구조는 공통 모듈이 여러 번 쓰이도록 들어오는 갈래는 늘리고, 한 모듈이 부르는 하위 모듈 수는 줄인다

## 코딩 표기법

- **헝가리안 표기법 (Hungarian Notation)** — 변수 이름 맨 앞에 그 변수의 자료형을 뜻하는 짧은 접두어를 붙여 쓰는 방식.
  - 예: `nCount`, `szName`, `bFlag`
- **카멜 표기법 (Camel Case)** — 여러 단어를 이어 쓸 때 첫 단어는 소문자로 시작하고, 뒤 단어들의 첫 글자만 대문자로 쓰는 방식.
  - 예: `userName`
- **파스칼 표기법 (Pascal Case)** — 여러 단어를 붙여 쓸 때 첫 단어를 포함한 모든 단어의 첫 글자를 대문자로 쓰는 방식.
  - 예: `UserName` (주로 클래스 이름)
- **스네이크 표기법 (Snake Case)** — 단어와 단어 사이를 밑줄(_)로 잇고 보통 소문자로만 쓰는 방식.
  - 예: `user_name`

## 기타

- **생성자 (Constructor)** — 객체가 만들어질 때 자동으로 호출되어 멤버 변수를 초기화하는 특수한 메서드.
  - 클래스와 이름이 같고 반환형이 없다
- **미들웨어 (Middleware)** — 운영체제와 응용 프로그램 사이, 또는 서로 다른 시스템 사이에서 통신과 데이터 교환을 중개하는 소프트웨어.
  - 예: RPC, MOM, ORB, TP-Monitor, WAS
- **플랫폼 (Platform)** — 여러 응용 서비스가 그 위에서 개발·실행될 수 있도록 공통 기반 환경을 제공하는 것.
  - 공급자와 사용자를 이어 가치를 만드는 생태계라는 뜻으로도 쓴다
