# 소프트웨어 개발 방법론 · 요구사항 · 프로젝트 관리

## 애자일 방법론

- **애자일 (Agile)** — 계획과 문서보다 고객과의 협업, 변화에 대한 빠른 대응을 중시하며 짧은 주기로 동작하는 결과물을 반복 전달하는 개발 방법론의 총칭.
- **XP (eXtreme Programming)** — 고객을 개발에 직접 참여시키고 1~3주의 짧은 반복으로 자주 배포하며, 짝 프로그래밍·테스트 우선 같은 실천 원리를 극단까지 적용하는 경량 개발 방식.
- **스크럼 (Scrum)** — 제품 책임자·조력자·개발팀이 2~4주 단위의 반복 주기를 돌며 매일 짧은 회의로 진척을 점검하는, 자기조직적 팀 중심의 관리 방식.

## XP 실천 원리

- **짝 프로그래밍 (Pair Programming)** — 두 개발자가 한 컴퓨터 앞에서 한 명은 코드를 입력하고 다른 한 명은 실시간으로 검토하며 역할을 번갈아 맡는 방식. 결함을 일찍 잡고 지식을 나눈다.
- **공동 코드 소유 (Collective Ownership)** — 담당 영역을 나누지 않고 팀원 누구나 시스템의 어떤 코드든 수정할 수 있도록 코드에 대한 책임을 팀 전체가 함께 지는 방식.
- **테스트 주도 개발 (TDD, Test-Driven Development)** — 기능 코드보다 실패하는 테스트를 먼저 작성하고, 그 테스트를 통과하는 최소한의 코드를 만든 뒤 구조를 다듬는 짧은 주기를 반복하는 기법.
  - Red → Green → Refactor
- **지속적 통합 (CI, Continuous Integration)** — 각자 작업한 코드를 공유 저장소에 하루에도 여러 번 병합하고, 병합할 때마다 자동 빌드·테스트를 돌려 충돌과 오류를 조기에 찾아내는 방식.
- **리팩토링 (Refactoring)** — 외부에서 보이는 동작은 그대로 두고 내부 구조만 개선해 중복을 없애고 읽기 쉽고 고치기 쉬운 코드로 다듬는 작업.
- **작은 릴리즈 (Small Releases)** — 동작하는 기능을 작은 단위로 자주 배포해 고객의 반응을 빨리 받고, 한 번에 큰 변경을 내보내는 위험을 줄이는 방식.
- **메타포 (Metaphor)** — 시스템의 구조와 동작을 팀원과 고객 모두가 이해하는 쉬운 비유나 공통 이야기로 표현해 의사소통과 용어를 통일하는 것.

## XP 핵심 가치 (5가지) (의단피용존)

- **의사소통 (Communication)** — 개발자·관리자·고객이 서로 자주 대화하며 정보를 공유하고 오해를 줄이는 것을 중시하는 가치.
- **단순성 (Simplicity)** — 지금 필요한 것만 가장 간결하게 설계·구현하고, 미래를 대비한다며 쓰이지 않을 기능을 미리 만들지 않는 것을 중시하는 가치.
- **피드백 (Feedback)** — 테스트 결과·고객 반응·동료 검토에서 나오는 반응을 빠르게 받아 곧바로 개선에 반영하는 것을 중시하는 가치.
- **용기 (Courage)** — 요구가 바뀌거나 설계가 잘못되었을 때 과감히 코드를 고치거나 버리고, 문제를 숨기지 않고 드러내는 태도를 강조하는 가치.
- **존중 (Respect)** — 팀원 각자의 능력과 기여를 인정하고 서로를 배려하며 함께 일하는 태도를 강조하는 가치.

## 스크럼 구성요소

- **제품 책임자 (PO, Product Owner)** — 만들 결과물의 비전을 정하고 요구사항 목록의 항목을 작성하며 우선순위를 결정하는 역할. 이해관계자의 의견을 대표한다.
- **스크럼 마스터 (Scrum Master)** — 팀이 정해진 규칙과 절차를 잘 따르도록 돕고 진행을 가로막는 장애 요소를 찾아 없애는 조력자 역할. 지시하는 관리자가 아니다.
- **백로그 (Backlog)** — 개발할 기능과 요구사항을 우선순위 순으로 정리해 두고 계속 갱신하는 목록. 전체 목록에서 이번 반복 주기에 처리할 항목만 골라 별도 목록을 만든다.
- **스프린트 (Sprint)** — 보통 2~4주로 고정된 짧은 개발 반복 주기. 이 기간 안에 선정한 작업을 끝내 실제로 동작하는 결과물을 만든다.
- **일일 스크럼 (Daily Scrum)** — 매일 같은 시간에 약 15분간 서서 진행하며 어제 한 일, 오늘 할 일, 막힌 문제를 공유하는 짧은 회의.
- **스프린트 리뷰 (Sprint Review)** — 반복 주기가 끝날 때 완성된 결과물을 이해관계자에게 시연하고 피드백을 받아 요구사항 목록에 반영하는 회의.
- **스프린트 회고 (Sprint Retrospective)** — 반복 주기를 마친 뒤 팀이 일하는 방식 자체를 돌아보며 잘된 점, 문제점, 다음에 바꿀 점을 정리하는 회의. 결과물보다 과정을 점검한다.
- **번다운 차트 (Burndown Chart)** — 세로축에 남은 작업량, 가로축에 시간을 두어 작업이 줄어드는 추세를 그린 그래프. 계획 대비 진척을 한눈에 보여 준다.

## 소프트웨어 생명주기 모형

- **폭포수 모형 (Waterfall Model)** — 각 단계를 순서대로 끝내고 검토·승인을 거친 뒤에야 다음 단계로 넘어가는 선형 순차 모델. 앞 단계로 되돌아가기 어렵고 가장 고전적이다.
- Q: 폭포수 모형의 단계 순서 — 타당성 검토 → 계획 → 요구 분석 → 설계 → 구현 → 테스트 → 유지보수
- **프로토타입 모형 (Prototype Model)** — 요구를 정확히 파악하려고 핵심 기능만 담은 견본을 먼저 만들어 사용자에게 보여 주고, 피드백을 받아 보완해 가는 모델.
- **나선형 모형 (Spiral Model)** — 여러 번의 반복 주기를 거치며 점진적으로 완성하되, 매 주기마다 위험을 분석하고 줄이는 데 중점을 둔 모델. 대규모·고위험 시스템에 맞다.
  - 보헴(Boehm) 제안
- Q: 나선형 모형의 4단계 순서 — 계획 수립 → 위험 분석 → 개발 및 검증 → 고객 평가

## 요구사항

- **기능적 요구사항 (Functional Requirements)** — 시스템이 무엇을 해야 하는지, 즉 제공할 기능과 입력·처리·출력 내용에 관한 요구.
  - 예: 회원 가입, 주문 조회
- **비기능적 요구사항 (Non-functional Requirements)** — 기능 자체가 아니라 성능·보안·가용성·사용성·제약 조건처럼 시스템이 얼마나 잘 동작해야 하는지에 관한 품질 요구.
- Q: 요구사항 개발 프로세스 순서 — 도출(Elicitation) → 분석(Analysis) → 명세(Specification) → 확인(Validation)

## 요구사항 분석 도구

- Q: 구조적 분석 도구 5가지 — 자료 흐름도(DFD) · 자료 사전(DD) · 소단위 명세서 · 개체 관계도(ERD) · 상태 전이도(STD)
- **자료 흐름도 (DFD, Data Flow Diagram)** — 처리 과정·자료 흐름·자료 저장소·외부 단말을 원·화살표·평행선·사각형으로 그려 자료가 시스템을 거치며 어떻게 변환되는지 나타내는 도식.
- **자료 사전 (DD, Data Dictionary)** — 자료 흐름도에 나오는 자료 항목의 이름·구성·의미를 `=` `+` `[ ]` `{ }` `( )` `* *` 같은 기호로 정의해 모아 둔 문서.
- **소단위 명세서 (Mini-Spec)** — 자료 흐름도의 가장 아래 단계 처리 과정이 수행하는 절차를 구조적 언어나 의사결정표 등으로 자세히 기술한 문서.
- **개체 관계도 (ERD, Entity Relationship Diagram)** — 업무에 필요한 개체와 그 속성, 개체 사이의 관계를 도형으로 표현해 데이터 구조를 나타내는 도식.
- **상태 전이도 (STD, State Transition Diagram)** — 시스템이 가질 수 있는 상태들과 어떤 사건이 일어나면 다른 상태로 바뀌는지를 그려 시간에 따른 동작을 표현하는 도식.
- **UML (Unified Modeling Language)** — 객체지향 시스템을 분석·설계할 때 구조와 동작을 다이어그램으로 표현하는 표준 모델링 언어.
  - 구성: 사물, 관계, 다이어그램

## 소프트웨어 재사용·재공학 (3R)

- **역공학 (Reverse Engineering)** — 이미 만들어진 시스템의 코드나 실행 파일을 분석해 설계 정보·명세 같은 상위 수준의 문서를 거꾸로 뽑아내는 기법.
- **재공학 (Re-engineering)** — 기존 시스템을 분석해 기능은 유지하면서 구조를 개선하거나 새 환경에 맞게 다시 구현해 유지보수성을 높이는 기법.
  - 과정: 분석 → 재구성 → 역공학 → 이관
- **재사용 (Reuse)** — 이미 검증된 기능·모듈·설계를 새 시스템 개발에 다시 활용해 비용과 기간을 줄이고 품질을 높이는 것.

## 비용 산정 — 하향식

- **전문가 판단 기법** — 경험이 풍부한 숙련자가 과거 유사 프로젝트를 근거로 비용을 직관적으로 추정하는 방식. 빠르지만 개인의 편견이 끼어들기 쉽다.
- **델파이 기법 (Delphi Method)** — 여러 전문가의 추정치를 조정자가 익명으로 모아 다시 돌려주는 과정을 반복해 합의된 값을 끌어내는 방식. 한 사람의 편견을 줄인다.

## 비용 산정 — 상향식

- **LOC 기법 (Lines of Code)** — 원시 코드 줄 수를 낙관치·중간치·비관치로 예측한 뒤 가중 평균으로 기대치를 구해 비용을 산정하는 방식.
  - 예측치 = (낙관치 + 4×중간치 + 비관치) ÷ 6
- **Man Month 기법** — 한 사람이 한 달 동안 해낼 수 있는 작업량을 기준 단위로 삼아 전체 노력과 기간을 산정하는 방식.
  - 노력 = LOC ÷ 1인당 월평균 생산 LOC, 기간 = 노력 ÷ 투입 인원

## 비용 산정 — 수학적

- **COCOMO (COnstructive COst MOdel)** — 보헴이 제안한 모델로, 예상 원시 코드 줄 수(KDSI)를 개발 유형별 공식에 넣어 필요한 노력(인·월)과 기간을 산출하는 방식.
- Q: COCOMO 개발 유형 3가지 (규모 기준) — 조직형(Organic, 5만 라인 이하) · 반분리형(Semi-detached, 30만 라인 이하) · 내장형(Embedded, 30만 라인 이상)
- **Putnam 모형** — 개발 생명주기 전 과정에 걸친 노력의 분포를 가정해 비용을 산정하는 모델. 레일리-노든(Rayleigh-Norden) 곡선에 기반한다.
  - 자동화 도구: SLIM
- **기능 점수 (FP, Function Point)** — 코드 줄 수 대신 입력·출력·조회·내부 파일·외부 인터페이스 같은 기능 요소의 수와 복잡도에 가중치를 매겨 규모와 비용을 산정하는 방식.
  - 자동화 도구: ESTIMACS

## 프로젝트 관리

- Q: 프로젝트 관리의 3P — 사람(People) · 문제(Problem) · 프로세스(Process)
- **간트 차트 (Gantt Chart)** — 각 작업의 시작일과 종료일을 가로 막대로 표시해 일정과 진척을 시간 축 위에 나타내는 도표. 작업 간 선후 관계를 보여 주는 데는 약하다.
- **PERT (Program Evaluation and Review Technique)** — 작업 간 선후 관계를 네트워크 도표로 그리고, 각 작업 기간을 낙관치·보통치·비관치 세 값으로 추정해 일정을 계산하는 기법.
  - 기대 시간 = (낙관 + 4×보통 + 비관) ÷ 6
- **CPM (Critical Path Method)** — 작업 간 선후 관계를 네트워크로 그린 뒤 처음부터 끝까지 가장 오래 걸리는 경로를 찾아 전체 최소 소요 기간과 여유가 없는 작업을 파악하는 기법.

## 형상 관리

- **형상 관리 (SCM, Software Configuration Management)** — 개발 중 생기는 코드·문서 같은 산출물의 변경을 식별하고 통제·추적해 일관성을 유지하는 활동.
  - 도구: Git, SVN, CVS
- Q: 형상 관리 절차 순서 — 형상 식별 → 형상 통제 → 형상 감사 → 형상 기록(상태 보고)
- **형상 통제 (Configuration Control)** — 산출물에 대한 변경 요청을 전담 위원회(CCB)가 검토·승인한 뒤에만 기준선에 반영되도록 관리하는 활동.
- **베이스라인 (Baseline, 기준선)** — 공식 검토와 승인을 거쳐 확정된 산출물의 상태. 이 시점 이후의 변경은 정해진 통제 절차를 거쳐야만 가능하다.

## 릴리즈 노트

- **릴리즈 노트 (Release Note)** — 배포하는 소프트웨어 버전의 새 기능, 고친 결함, 변경 사항, 알려진 문제 등을 정리해 사용자에게 알리는 문서.
- **헤더 (Header)** — 배포 안내 문서의 맨 앞 항목으로 문서 이름, 제품 이름, 버전 번호, 배포일, 참고 날짜 등을 적는 부분.
- Q: 릴리즈 노트 작성 항목 순서 — 헤더 → 개요 → 목적 → 문제 요약 → 재현 항목 → 수정/개선 내용 → 사용자 영향도 → SW 지원 영향도 → 노트 → 면책 조항 → 연락처

## 소프트웨어 아키텍처 패턴

- **레이어 패턴 (Layers Pattern)** — 시스템을 위아래 여러 층으로 나누어 각 층이 바로 아래 층의 서비스만 사용하고 위 층에는 서비스를 제공하도록 구성하는 구조.
  - 예: OSI 7계층
- **클라이언트-서버 패턴 (Client-Server Pattern)** — 하나의 중앙 컴포넌트가 여러 요청 측 컴포넌트에 서비스를 제공하는 구조. 요청 측이 요청을 보내면 제공 측이 처리해 응답한다.
- **파이프-필터 패턴 (Pipe-Filter Pattern)** — 데이터 스트림을 처리하는 각 단계를 독립 컴포넌트로 캡슐화하고 통로로 이어, 한 단계의 출력이 다음 단계의 입력이 되게 하는 구조.
  - 예: UNIX 셸 명령 연결
- **브로커 패턴 (Broker Pattern)** — 분산된 컴포넌트들 사이에서 중개 컴포넌트가 요청을 받아 알맞은 서버로 전달하고 결과를 돌려주며 통신을 조정하는 구조.
  - 예: CORBA
- **피어 투 피어 패턴 (Peer-to-Peer Pattern)** — 각 컴포넌트가 상황에 따라 요청하는 쪽과 서비스하는 쪽 역할을 모두 맡아 서로 대등하게 통신하는 구조.
  - 예: 파일 공유
- **이벤트-버스 패턴 (Event-Bus Pattern)** — 발행자가 특정 채널에 메시지를 보내면 그 채널을 구독한 수신자들이 메시지를 받아 처리하는 구조.
  - 구성: 소스, 리스너, 채널
- **MVC 패턴 (Model-View-Controller Pattern)** — 애플리케이션을 데이터와 핵심 로직, 사용자에게 보여 주는 화면, 입력을 받아 둘을 조정하는 부분의 세 구성요소로 분리하는 구조.
- **마스터-슬레이브 패턴 (Master-Slave Pattern)** — 주 컴포넌트가 같은 구조의 하위 컴포넌트들에 작업을 나눠 주고, 하위 컴포넌트가 돌려준 결과를 모아 최종 결과를 만드는 구조.
  - 예: DB 복제
- **블랙보드 패턴 (Blackboard Pattern)** — 정해진 해결 전략이 없는 문제에서 여러 지식 소스가 공유 저장소에 부분 해를 쓰고 읽으며 협력해 답을 찾아가는 구조.
  - 예: 음성 인식
- **인터프리터 패턴 (Interpreter Pattern)** — 특정 언어로 작성된 프로그램이나 문장을 해석해 실행하는 컴포넌트를 설계하는 구조.
  - 예: 질의 언어 해석기

## 연계 요구사항 분석 기법

- **인터뷰 (Interview)** — 이해관계자를 직접 만나 묻고 답하며 요구사항을 수집하는 기법. 자세한 정보를 얻을 수 있지만 시간이 많이 든다.
- **체크리스트 (Checklist)** — 미리 정리해 둔 점검 항목 목록에 따라 연계 대상 시스템의 요구사항을 빠짐없이 확인하는 기법.
- **설문지 (Questionnaire)** — 정해진 질문 양식을 다수의 관계자에게 배포하고 회수해 요구사항을 수집하는 기법. 짧은 시간에 많은 의견을 모을 수 있다.
- **델파이 기법 (Delphi Method)** — 여러 전문가에게 익명으로 의견을 받아 정리·공유하는 과정을 되풀이해 합의된 요구사항을 도출하는 기법.
- **브레인스토밍 (Brainstorming)** — 여러 참여자가 비판 없이 자유롭게 아이디어를 쏟아낸 뒤 이를 정리해 요구사항을 발굴하는 회의 기법.
