# 영역 1 · 책임 있는 AI

## 여섯 가지 원칙

- **공정성 (Fairness)** — 결과와 상관없는 성별·나이·민족 같은 속성 때문에 처지가 비슷한 사람들이 서로 다른 대우를 받지 않도록 AI를 만들어야 한다는 원칙
  - 사람이 고르고 모은 학습 데이터에 무의식적 편향이 섞이면 차별적인 출력이 나올 수 있다
- **신뢰성 및 안전성 (Reliability and safety)** — 시스템이 설계한 대로 일관되게 동작하고, 예상 밖의 입력이나 악의적 조작에도 해를 끼치지 않게 대응해야 한다는 원칙
  - AI는 확률 모델이라 틀릴 수 있다는 전제에서 출발한다
- **개인정보 보호 및 보안 (Privacy and security)** — 학습과 예측에 쓰이는 개인·조직 데이터를 안전하게 지키고, 학습이 끝난 모델로 그 세부 내용을 알아낼 수 없게 해야 한다는 원칙
- **포용성 (Inclusiveness)** — 신체 능력·성별·민족 등과 관계없이 누구나 AI의 혜택을 누리고 이용에서 배제되지 않도록 설계해야 한다는 원칙
- **투명성 (Transparency)** — 사용자가 시스템의 목적, 작동 방식, 예상되는 한계를 알 수 있게 해야 한다는 원칙
  - 핵심 요소는 해석 가능성(interpretability), 즉 모델이 왜 그런 결과를 냈는지 사람이 이해할 수 있게 설명하는 능력
- **책임성 (Accountability)** — AI를 만들고 배포한 사람과 조직이 시스템의 결과를 끝까지 떠안고, 이를 보장할 거버넌스 체계를 갖춰야 한다는 원칙
  - 사람의 삶에 영향을 주는 결정에서 AI가 최종 권한자가 되지 않게 사람이 통제권을 유지한다
- Q: Microsoft 책임 있는 AI의 여섯 원칙 — 공정성, 신뢰성 및 안전성, 개인정보 보호 및 보안, 포용성, 투명성, 책임성
- Q: Microsoft가 여섯 원칙을 바탕으로 자기 엔지니어링 팀에 적용하는 정책 문서 — Microsoft Responsible AI Standard

## 시나리오로 원칙 고르기

- Q: 대학 입학 심사 AI가 학업 기준과 무관한 인구통계 정보로 지원자를 차별하지 않는지 시험한다. 해당 원칙 — 공정성
- Q: 공정성을 위해 개발 초기부터 할 일 두 가지 — 학습 데이터가 영향받는 집단을 고루 대표하는지 검토, 집단별로 예측 성능을 나눠 평가
  - 도구만으로는 충분하지 않고 개발 수명 주기 내내 따져야 한다
- Q: 물체를 인식해 집는 로봇이 인식 신뢰도가 기준값보다 낮으면 동작하지 않게 했다. 해당 원칙 — 신뢰성 및 안전성
- Q: 자율주행차나 증상을 보고 처방을 권하는 의료 AI에서 특히 무게가 실리는 원칙 — 신뢰성 및 안전성
  - 오작동이 곧 사람의 생명에 대한 위험이다
- Q: 공항 얼굴 인식 시스템이 임시 출입용 사진을 용도가 끝나면 바로 지우고, 볼 필요 없는 직원의 접근을 막는다. 해당 원칙 — 개인정보 보호 및 보안
- Q: 음성으로 대화하는 AI 에이전트가 청각 장애 사용자를 위해 텍스트 자막을 함께 낸다. 해당 원칙 — 포용성
- Q: 포용성을 높이는 개발 방식 — 설계·개발·테스트에 가능한 한 다양한 사람의 의견을 반영
- Q: 은행이 대출 심사에 AI를 쓴다는 사실과 학습 데이터의 특징을 고객에게 밝힌다. 해당 원칙 — 투명성
  - 기밀 정보까지 공개하라는 뜻은 아니다
- Q: 투명성을 위해 사용자에게 알려 줄 만한 정보 예 — 학습에 쓴 사례 수, 예측에 가장 영향이 큰 특성, 예측의 신뢰도 점수
- Q: 챗봇 답변 아래에 AI가 만든 내용이라 틀릴 수 있다는 안내를 붙였다. 해당 원칙 — 투명성
- Q: 조직이 AI 개발 전체에 적용할 거버넌스 체계와 내부 기준을 정했다. 해당 원칙 — 책임성
- Q: Azure OpenAI 같은 서비스의 알려진 한계와 사용 시 고려사항을 확인할 수 있는 Microsoft 문서 — Transparency Note (투명성 노트)

## 헷갈리는 짝

- Q: 투명성과 책임성의 차이 — 투명성은 작동 방식과 한계를 알리는 것, 책임성은 결과를 사람과 조직이 떠안는 것
- Q: 공정성과 포용성의 차이 — 공정성은 사람을 차별 없이 대하는 것, 포용성은 누구도 이용에서 빠지지 않게 하는 것
- Q: 시각 장애인이 화면 낭독 프로그램으로는 앱을 쓸 수 없다. 공정성과 포용성 중 어느 쪽 문제 — 포용성
- Q: 고객이 자기 대출이 왜 거절됐는지 설명을 들을 수 있어야 한다. 투명성과 책임성 중 어느 쪽 — 투명성
- Q: 위험한 결정은 AI가 아니라 담당자가 최종 승인하도록 절차를 만들었다. 투명성과 책임성 중 어느 쪽 — 책임성
- Q: 개인정보가 담긴 학습 데이터를 암호화하고 접근 권한을 제한했다. 공정성과 개인정보 보호 및 보안 중 어느 쪽 — 개인정보 보호 및 보안

## Azure Machine Learning의 원칙 지원 도구

- Q: Responsible AI dashboard에서 성별·나이 같은 민감 집단별 성능 차이를 보는 구성 요소와 관련 원칙 — fairness assessment, 공정성
- Q: 오류율이 유독 높은 데이터 하위 집단(cohort)을 찾는 dashboard 구성 요소와 관련 원칙 — error analysis, 신뢰성 및 안전성
- Q: 모델 예측을 사람이 이해할 수 있는 설명으로 바꿔 주는 dashboard 구성 요소 두 가지 — model interpretability, counterfactual what-if
  - 둘 다 투명성 원칙을 돕는다
- **Responsible AI scorecard** — 데이터와 모델의 상태를 기술 담당자와 비기술 이해관계자가 함께 볼 수 있게 만든, 항목을 고를 수 있는 PDF 보고서
  - Azure Machine Learning에서 만들며 투명성과 책임성을 함께 뒷받침한다

## 책임 있는 생성형 AI 절차

- Q: Learn 교육 과정이 제시하는 책임 있는 생성형 AI 4단계 — Map, Measure, Mitigate, Manage
  - NIST AI Risk Management Framework의 기능과 거의 대응한다
- Q: Map 단계 안의 네 단계 순서 — 잠재적 해악 식별, 우선순위 결정, 테스트로 실제 발생 확인, 문서화와 공유
- Q: 해악의 우선순위를 정할 때 따지는 두 가지 — 일어날 가능성, 일어났을 때의 영향 크기
- **레드 팀 (Red teaming)** — 테스터들이 일부러 시스템의 약점을 파고들어 해로운 결과를 끌어내 보는 시험 방식. 보안 분야 관행을 생성형 AI의 유해 출력 탐색으로 넓혀 쓴다
- Q: Measure 단계의 세 단계 — 해악을 유도할 프롬프트 준비, 시스템에 넣어 출력 수집, 미리 정한 기준으로 출력 분류
- Q: Measure 단계가 만드는 것과 그 용도 — 해악 수준의 기준선(baseline), 완화 조치 뒤 개선 정도를 비교
- Q: Mitigate 단계에서 완화를 거는 네 계층 — 모델, 안전 시스템, 시스템 메시지와 그라운딩, 사용자 경험
- Q: 짧은 텍스트 분류만 하면 되는 앱에 범용 대형 모델 대신 단순한 모델을 고르거나 파인튜닝한다. 어느 완화 계층 — 모델 계층
- Q: Foundry의 guardrails, 콘텐츠 필터, prompt shields가 속하는 완화 계층 — 안전 시스템 계층
- Q: 시스템 메시지로 행동 범위를 정하고 RAG로 신뢰할 수 있는 자료를 프롬프트에 넣는다. 어느 완화 계층 — 시스템 메시지와 그라운딩 계층
- Q: 입력 주제를 화면에서 제한하고, 문서에 시스템의 한계와 남은 위험을 밝힌다. 어느 완화 계층 — 사용자 경험 계층
- Q: 출시 전에 받아야 할 대표적인 규정 준수 검토 네 가지 — 법무, 개인정보, 보안, 접근성
- Q: 처음에는 제한된 사용자에게만 공개해 피드백을 모은 뒤 넓히는 계획 — 단계적 출시 계획 (phased delivery plan)
- Q: Manage 단계에서 운영 중 갖춰 둘 기능 예 — 유해 응답 즉시 차단, 오남용 사용자·앱·IP 차단, 사용자 신고 창구
- Q: Microsoft Foundry 문서가 에이전트 수명 주기에 맞춰 제시하는 책임 있는 AI 3단계 — Discover, Protect, Govern
  - Discover는 배포 전후의 위험 발견, Protect는 모델 출력과 에이전트 실행 단계 방어, Govern은 추적·모니터링·규정 준수
- Q: 적대적 프롬프트로 에이전트의 탈옥 취약점을 찾는 일은 Discover, Protect, Govern 중 어디 — Discover

## Foundry guardrails

- **Guardrail (Foundry)** — 탐지할 위험, 검사할 위치, 탐지 시 조치를 하나씩 정한 control들을 이름 붙여 묶은 것. 모델 배포와 에이전트에 적용한다
  - 예전 이름: content filters (콘텐츠 필터)
- Q: guardrails가 해로운 콘텐츠를 판별할 때 쓰는 분류 모델의 출처 서비스 — Azure AI Content Safety
- Q: 콘텐츠 유해성의 네 가지 범주 — 증오(hate and fairness), 성적(sexual), 폭력(violence), 자해(self-harm)
- Q: 유해 범주마다 매기는 네 가지 심각도 — safe, low, medium, high
  - safe는 주석(annotation)으로만 표시되고 차단·설정 대상이 아니다
- Q: guardrail의 네 가지 개입 지점(intervention point) — User input, Tool call, Tool response, Output
  - Tool call과 Tool response는 에이전트에만 해당한다(preview)
- Q: 모델 배포에 기본으로 붙는 guardrail 이름 — Microsoft.DefaultV2
- Q: 에이전트에 guardrail을 따로 지정하지 않았을 때 적용되는 것 — 그 에이전트가 쓰는 모델 배포의 guardrail
  - 에이전트에 직접 지정하면 모델 쪽 guardrail을 완전히 대체한다
- Q: 사용자가 시스템 규칙을 바꾸라고 하거나 다른 페르소나를 씌워 제한을 풀려는 시도를 잡는 기능 — Prompt Shields (user prompt attacks)
- Q: 모델이 읽는 문서나 이메일 안에 제3자가 악성 지시를 숨겨 두는 공격 — 간접 공격 (Indirect attacks)
  - Cross-Domain Prompt Injection Attacks라고도 부른다
- Q: 노래 가사·기사 같은 알려진 텍스트나 공개 저장소 코드와 일치하는 출력을 잡는 필터 — Protected material (text, code)
- Q: 에이전트의 도구 호출이 사용자 의도와 어긋나는지 감지하는 guardrail 위험 항목 — Task Adherence (preview)
- Q: 프롬프트가 필터 기준에 걸렸을 때 API가 돌려주는 것 — HTTP 400 오류
- Q: 생성 결과가 필터에 걸렸을 때 응답의 `finish_reason` 값 — `content_filter`
